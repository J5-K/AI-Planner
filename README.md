# AI 동적 플래너

사용자가 해야 할 일을 자연어로 입력하면 계획에 필요한 정보를 구조화하고, 부족한 조건을 질문으로 보완한 뒤 실행 가능한 일정을 생성하는 LangChain 기반 플래너입니다. 최초 계획이 어긋나거나 새로운 일정이 생겼을 때 완료하지 못한 작업을 남은 시간에 재배치하는 것을 목표로 합니다.

## 프로젝트 목표

혼자 계획을 구체화하기 어렵거나, 계획이 한 번 어긋난 뒤 다시 조정하기 어려운 사용자를 돕습니다.

사용자가 할 일만 입력해도 다음 과정을 통해 현실적인 계획을 만들 수 있어야 합니다.

```text
할 일 입력
→ 할 일과 제약 조건 구조화
→ 부족한 정보 질문
→ 최초 계획 생성
→ 시간 및 일정 충돌 검증
→ 수행 결과와 새 일정 입력
→ 미완료 작업 재계획
```

## 핵심 기능

1. **할 일 구조화**
   - 자연어 입력에서 작업, 마감일, 예상 시간, 우선순위 등을 추출합니다.
2. **부족한 정보 질문**
   - 계획 생성에 필요한 정보가 없으면 이를 판별하고 추가 질문을 생성합니다.
3. **계획 생성**
   - 작업을 우선순위, 마감일, 가용 시간에 맞게 배치합니다.
4. **시간 검증**
   - 작업시간 합계와 가용 시간을 비교하고 과부하 및 일정 충돌을 확인합니다.
5. **미완료 작업 재계획**
   - 완료하지 못한 작업과 새로 생긴 고정 일정을 반영해 남은 계획을 수정합니다.

## 왜 LLM이어야 하는가

사용자는 “다음 주 금요일까지”, “오전에는 공부하고 싶다”, “추석 연휴에는 안 된다”처럼 형식이 일정하지 않은 자연어로 계획을 말합니다. 같은 뜻도 사람마다 다르게 표현하며, 목표와 실제 행동, 반복 작업, 고정 일정, 선호 시간대를 문장 안에서 구분해야 합니다. 이를 모든 문장 패턴에 대한 규칙으로 작성하면 예외가 빠르게 늘어납니다.

따라서 LLM은 다음처럼 의미 해석이 필요한 부분에만 사용합니다.

- 자연어를 계획 데이터로 구조화
- 현재 입력에서 정말 필요한 후속 질문 선택
- 작업의 논리적인 선후관계 판단과 이유 설명

반대로 날짜 계산과 충돌 판정을 LLM에 맡기면 그럴듯하지만 틀린 시간이 나올 수 있으므로 Python의 결정적 로직으로 처리합니다.

## 컨텍스트 엔지니어링과 LangChain 구성

| 단계 | 입력 컨텍스트 | 사용 컴포넌트 | 사용 이유와 없을 때의 문제 |
| --- | --- | --- | --- |
| 입력 구조화 | 오늘 날짜, 사용자 원문, 목표·작업 구분 규칙, 날짜·시간 형식 | `ChatPromptTemplate`, LCEL, Pydantic Structured Output | 자유 형식 답변이면 후속 Python 로직이 필드를 안정적으로 읽을 수 없음 |
| 후속 질문 | 현재 구조화 결과와 Python이 계산한 누락 항목 | 별도 질문 Chain | 모든 사용자에게 같은 질문을 하면 이미 말한 내용을 다시 묻고 UX가 나빠짐 |
| 계획 순서 판단 | 목표, 기간, 작업, 고정 일정 | 계획 Chain + Structured Output | Python만으로는 “주제 선정 → 개발 → 테스트” 같은 의미적 선후관계를 일반화하기 어려움 |
| 시간 배치·검증 | 구조화된 작업, 가용 슬롯, 고정 일정 | Python scheduler | LLM만 사용하면 시간 겹침, 잘못된 요일, 가용 시간 초과가 발생할 수 있음 |
| 캘린더 확인 | 직렬화된 `PlanningContext` 또는 `Plan` | LangChain `@tool` 2개 | 계획 생성과 일정 조회·충돌 확인의 인터페이스가 분리되지 않음 |
| 재계획 | 기존 계획, 미완료 작업, 새 종일·시간 일정 | 재계획 흐름 + Python 재배치 | 기존 결과를 무시하고 전체를 새로 만들면 완료 작업이 사라지거나 반복 횟수가 달라짐 |

사용한 핵심 LangChain 컴포넌트는 다음 네 종류입니다.

1. `ChatPromptTemplate`: 역할과 입력 컨텍스트, 제약 조건을 단계별로 분리합니다.
2. LCEL Chain: `prompt | structured_model` 형태로 입력부터 모델 출력까지 연결합니다.
3. Pydantic Structured Output: 모델 출력을 `PlanningContext`, `PlanningDecision`, `PlanUpdate` 스키마로 고정합니다.
4. LangChain Tool: 가상 캘린더 일정 조회와 계획 충돌 검사를 호출 가능한 도구로 제공합니다.

## 설치 및 실행

### 1. 가상환경 생성

macOS/Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

Windows PowerShell:

```powershell
py -m venv .venv
.venv\Scripts\Activate.ps1
```

### 2. 패키지 설치

```bash
python -m pip install -r requirements.txt
```

### 3. 환경변수 설정

`.env.example`을 복사해 `.env`를 만들고 OpenAI API 키를 입력합니다.

macOS/Linux:

```bash
cp .env.example .env
```

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

```dotenv
OPENAI_API_KEY=your_api_key_here
```

`.env`는 Git에 커밋하지 않습니다.

### 4. 실행

현재 입력 구조화 테스트:

```bash
python app.py
```

터미널에서 질문에 답하려면 `python app.py`를 실행합니다.

웹 화면으로 실행하려면 다음 명령을 사용합니다.

```bash
python gradio_app.py
```

출력된 로컬 주소(일반적으로 `http://127.0.0.1:7860`)를 브라우저에서 엽니다.
최초 계획을 만든 뒤 `계획이 어긋났나요? 재계획하기` 영역에 미완료 작업과
새 약속을 자연어로 입력하면 남은 작업을 다시 배치할 수 있습니다.

웹 화면에서는 다음 기능을 추가로 제공합니다.

- 체크박스로 미완료 작업 선택
- 새 약속을 날짜와 시작·종료 시간으로 입력
- 최초 계획과 재계획의 유지·이동·추가·제외 항목 비교
- 재계획 후 새 고정 일정과 변경 계획을 상태·주간 캘린더·날짜별 상세에 동시에 반영
- 계획 기간 밖의 새 일정은 숨기지 않고 기간 조정 안내 표시
- 일정 표에서 날짜와 시간을 직접 수정한 뒤 재검증
- LangChain 가상 캘린더 Tool을 통한 고정 일정 조회와 충돌 검사
- 원문 기반 요일 불가 조건 재검증 (`토요일 불가` 등)
- `이번 주·다음 주 + 요일` 상대 마감일을 Python으로 재검증
- 빠른 완료·균등 분산·여유일 확보 계획 방식 선택
- 계획 기간과 실제 예상 완료일 비교 안내
- 계획에 실제 반영된 평일·주말·요일별 가용 시간 표시
- 여러 주를 날짜별 카드로 보여주는 주간 캘린더
- 새 일정을 `종일·기간 일정` 또는 `시간 지정 일정`으로 구분
- 종일 일정은 시작일부터 종료일까지의 가용 시간을 전체 차단
- 반복 작업은 실제 가용 날짜에만 생성하고 사용자 화면에서 회차 번호를 숨김
- `오전 공부`, `저녁 운동`과 같은 작업별 선호 시간대 반영
- 미배치 발생 시 여유일 사용·추가 가능 시간 등록 버튼 제공
- 사용자가 새 종료일을 선택하면 기존 일정과 반복 횟수는 유지하고 미배치 작업만 연장 구간에 배치
- 마감이 있는 일회성 핵심 작업을 공부·운동 같은 반복 루틴보다 우선 배치

## 데이터 모델

| 모델              | 역할                                                |
| ----------------- | --------------------------------------------------- |
| `Task`            | 작업명, 예상 시간, 마감일, 우선순위, 분할 가능 여부 |
| `RecurrenceRule`  | 매일·매주·매월 및 간격을 표현하는 반복 규칙         |
| `FixedEvent`      | 변경할 수 없는 단일 또는 반복 일정                  |
| `AvailableSlot`   | 특정 날짜 또는 반복 요일의 작업 가능 시간대         |
| `PlanningContext` | 목표, 작업, 가용 시간, 누락 정보 등 계획 전체 조건  |
| `ScheduleItem`    | 특정 날짜와 시간에 배치된 작업                      |
| `Plan`            | 생성된 전체 일정과 경고 및 설명                     |
| `PlanUpdate`      | 완료, 미완료, 새 고정 일정 등 변경 사항             |

## 시연 시나리오

### 최초 입력

```text
이번 주 일요일까지 LangChain 프로젝트를 완성해야 한다.
해야 할 일은 주제 확정, 핵심 기능 개발, UI 구현, 발표 자료 작성이다.
수요일 저녁에는 약속이 있다.
```

AI는 작업별 예상 시간, 하루 가용 시간, 우선순위, 작업 분할 가능 여부 등 부족한 정보를 질문합니다.

### 계획 실패 및 새 일정

```text
화요일의 핵심 기능 개발을 완료하지 못했다.
목요일 저녁에도 새로운 약속이 생겼다.
```

### 기대 결과

- 완료한 작업은 유지합니다.
- 미완료 작업은 남은 시간으로 이동합니다.
- 새 약속과 충돌하는 작업을 재배치합니다.
- 마감일과 우선순위를 유지합니다.
- 시간이 부족하면 일정을 억지로 배치하지 않고 경고와 축소안을 제시합니다.

## 완료 조건

다음 흐름이 한 번에 동작하면 MVP가 완성된 것으로 판단합니다.

1. 사용자가 LangChain 프로젝트 준비 작업을 입력합니다.
2. AI가 입력을 구조화하고 부족한 정보를 질문합니다.
3. 답변을 반영해 최초 계획을 생성합니다.
4. 사용자가 미완료 작업과 새로운 약속을 입력합니다.
5. 완료한 작업은 유지하면서 남은 작업이 충돌 없이 재배치됩니다.
6. 변경된 일정과 변경 이유가 표시됩니다.

## 설계 원칙

- LLM은 자연어 이해, 누락 정보 판단, 우선순위 해석, 변경 이유 설명을 담당합니다.
- Python은 시간 합산, 슬롯 계산, 충돌 검사 등 정확한 계산을 담당합니다.
- 사용자가 제공하지 않은 날짜와 시간을 사실처럼 생성하지 않습니다.
- 가용 시간보다 필요한 시간이 많으면 경고하고 사용자에게 범위 조정을 요청합니다.
- 실제 캘린더 저장이나 외부 서비스 변경은 사용자 승인 없이 수행하지 않습니다.

## 트러블슈팅 기록

### 1. 시간 문자열과 정수 스키마 충돌

- 증상: `20:00` 같은 값을 `available_minutes_per_day`의 정수 필드에 넣어 Pydantic 검증 오류가 발생했습니다.
- 원인: “몇 분 가능한가”와 “몇 시부터 몇 시까지 가능한가”를 하나의 자료형으로 표현했습니다.
- 해결: `AvailableSlot`을 만들고 `start_time`, `end_time`, `available_minutes`를 분리했습니다.

### 2. “매주 수요일”이 한 번만 반영됨

- 증상: 반복 약속이 최초 날짜 한 건으로만 저장됐습니다.
- 원인: 단일 날짜와 반복 규칙을 구분하는 모델이 없었습니다.
- 해결: `RecurrenceRule`을 추가하고 일·주·월 단위 규칙을 계획 기간의 실제 날짜로 확장했습니다.

### 3. 질문이 너무 많고 딱딱함

- 증상: 모든 예상 시간과 가용 시간을 분 단위로 요구해 사용 부담이 커졌습니다.
- 원인: 누락된 필드를 그대로 하나씩 질문했습니다.
- 해결: Python에서 관련 누락 항목을 묶고, 꼭 필요한 경우에만 최대 4개 질문하며 모르는 시간은 AI 임시 추정값으로 초안을 만들게 했습니다.

### 4. 상대 날짜와 불가 요일 오해

- 증상: “다음 주 금요일”을 이번 주로 계산하거나 “토요일 불가”를 다른 요일로 해석하는 경우가 있었습니다.
- 원인: 날짜 계산을 전적으로 LLM 출력에 의존했습니다.
- 해결: 사용자 원문을 기준으로 상대 날짜와 불가 요일을 Python에서 다시 보정합니다.

### 5. 반복 작업 회차가 뒤섞임

- 증상: 운동 3회차보다 10회차가 먼저 보이거나, 가용 시간이 없는 날의 반복 작업까지 생성됐습니다.
- 원인: 전체 기간의 반복 인스턴스를 먼저 만들고 나중에 배치했습니다.
- 해결: 실제 가용 날짜를 기준으로 주별 반복 인스턴스를 생성하고, 화면에는 불필요한 회차 번호를 숨겼습니다.

### 6. 재계획에서 기존 작업이 사라짐

- 증상: 미완료 작업 하나를 재계획하면 이후 작업이 제외되거나 새 종일 일정과 기존 작업이 함께 남았습니다.
- 원인: 새 입력만으로 계획을 다시 만들거나 종일 기간을 정확히 차단하지 못했습니다.
- 해결: 기존 계획 중 영향받기 전 일정은 보존하고, 실패 작업과 이후 일정만 재배치합니다. 종일·기간 일정은 해당 날짜 범위의 가용 슬롯 전체를 차단합니다.

### 7. 기간 연장 시 반복 횟수 증가

- 증상: 미배치 작업을 해결하려고 기간을 늘리면 운동·공부 반복 횟수까지 새로 늘어났습니다.
- 원인: 연장 시 전체 `PlanningContext`로 계획을 다시 생성했습니다.
- 해결: `Plan.unscheduled_tasks`에 미배치 작업을 보존하고, 사용자가 선택한 연장 구간에는 해당 작업만 배치합니다. 기존 일정과 반복 횟수는 유지합니다.

### 8. 추가 답변의 주말 시간이 사라짐

- 증상: 평일과 주말 시간을 모두 답했지만 계획에는 평일만 반영되고, 미배치 작업이 주말을 건너뛰어 다음 평일에 배치됐습니다.
- 원인: 여러 줄 답변을 질문 수만큼만 연결해 남는 줄을 버렸고, LLM이 `available_slots` 목록을 다시 작성하면서 주말 슬롯을 누락해도 이를 검증하지 않았습니다.
- 해결: 번호가 있는 답변은 다음 번호 전까지 여러 줄을 한 답변으로 묶고, 번호가 없는 추가 줄도 버리지 않고 컨텍스트에 포함합니다. 또한 명시적인 평일·주말·요일 시간 범위를 Python으로 재검증해 누락된 슬롯을 복원하고 결과 화면에 인식한 가용 시간을 표시합니다.

## 한계와 개선 방향

### 현재 한계

- 자연어 구조화와 작업 순서 판단은 확률적인 LLM 출력이므로 같은 의미의 입력도 세부 결과가 달라질 수 있습니다.
- “프로젝트를 완성한다”처럼 작업이 추상적이면 사용자가 구체적인 실행 작업을 제공해야 하며, 현재 서비스가 목표 달성에 충분한 작업 목록까지 보장하지는 않습니다.
- 예상 시간이 없을 때 사용하는 AI 임시 시간은 개인의 실제 속도를 반영하지 못합니다.
- 현재 임시 추정은 특정 예시에 편향된 키워드 사전을 사용하지 않고 모든 미입력 작업에 60분을 적용하므로, 작업 난이도 차이를 반영하지 못합니다.
- 작업은 현재 하나의 연속된 슬롯에 배치합니다. `splittable` 필드는 있지만 긴 작업을 여러 날로 자동 분할하는 기능은 완성되지 않았습니다.
- 의존관계는 별도 그래프가 아니라 프롬프트의 순서 판단에 의존하므로 복잡한 프로젝트에서는 순서가 부정확할 수 있습니다.
- 재계획은 현재 선택한 미완료 작업과 그 이후 일정을 대상으로 하며, 완료 상태의 영구 저장이나 여러 버전 복원 기능은 없습니다.
- 가상 캘린더 Tool은 조회와 검증용이며 실제 Google Calendar에 일정을 쓰지 않습니다.
- 로그인, 알림, 데이터베이스가 없어 브라우저를 닫으면 사용자별 계획을 장기 보존하지 않습니다.

### 개선 방향

1. 실제 소요 시간과 작업 유형을 기록해 범용 기본값 60분 대신 사용자별·작업별 예상 시간 보정 모델을 만듭니다.
2. 작업 의존관계를 명시적인 DAG로 관리하고 선행 작업이 끝난 뒤 후속 작업을 배치합니다.
3. 긴 작업을 최소 블록 단위로 나누는 분할 스케줄링을 구현합니다.
4. 사용자가 미배치 경고에서 바로 “시간 추가·작업 축소·종료일 연장”을 선택하도록 상호작용을 강화합니다.
5. 사용자 승인 후 Google Calendar API에 최종 계획을 저장하는 Tool을 추가합니다.
6. 계획 이력과 완료율을 데이터베이스에 저장하고 재계획 품질을 평가합니다.
